1 · What is a climate cube?

Dimensions, variables and the idea behind the cube

What is a climate data cube?

A data cube is a multidimensional way to organize data. A climate data cube applies this idea to climate or Earth observation variables, commonly indexed by: 

time
latitude
longitude
variable
  • Climate cube: gives climate/EO data meaningful arrangement of variables, coordinates and time steps - that allows a harmonized, analysis-ready view of the data.
  • It is a domain-focused data organization, not a separate file format. Here, NetCDF is the input and Zarr is the output.

2 · Why are we here?

And why use a cube at all?

Why are we here?

Climate products are useful, but their files can arrive with different grids, time steps, metadata and quality information.

Today we make one small, transparent processing path from EUMETSAT source files to a regional data cube.

We will learn how to work with data cubes in a practical setting, using real-world examples and tools.

What will we learn?

Find and download a selected LSA SAF product safely.

Crop and remap a sample to an explicitly defined regional grid.

Build and inspect a chunked, compressed Zarr cube.

Why use a cube?

Many separate files One cube
Different grids, time steps and naming One grid, one time axis, named variables
Open and loop over files Open once, select by label (time, lat, lon)
Read whole files Read only the chunks you need
Processing choices live in scripts and memory Choices can be documented with the data

Where a cube fits in the ecosystem

Describe
Standardise metadata for discovering geospatial assets.

Discover and process
Access open datasets through STAC and use hosted compute.

Analyse
Use a managed platform for large-scale geospatial analysis.

Store
Save chunked, compressed multidimensional arrays.

Work with data
Select, transform and analyse labelled arrays in Python.

These tools have different roles and can be combined in different workflows. STAC describes and helps discover assets; it is not a data cube format. Planetary Computer and Earth Engine are hosted platforms with different data catalogues and processing models. Zarr is a storage format, while Xarray is a Python library for working with labelled arrays.

Where does our data come from?

Product What it represents In this tutorial
METREF Reference evapotranspiration Default configured download sample
FVC / MDFVC Fractional vegetation cover Additional product example; configure its own URL and metadata

Data are accessed from the authenticated LSA SAF Data Service. Availability, versions, units, coverage and quality depend on the product; check its product page before analysis.

3 · Our approach

Small, explicit, checkable

From source file to cube

Each step leaves a checkable output. If a stage fails, diagnose that stage before moving on.

Three principles

Small first

One product, one month, one region.

Explicit

Bounds, grid, resampling and chunking are written down.

Checkable

Every stage leaves an output you can inspect.

APIs, cloud platforms and this workflow

APIs, Microsoft Planetary Computer and Google Earth Engine are useful for discovering, accessing and analyzing many datasets.

This tutorial demonstrates a local, explicit path for selected authenticated LSA SAF data when we need to document a regional crop, target grid and processing choices. The two approaches can complement each other; this workflow does not assume hosted platforms lack the required data.

4 · Tutorial walkthrough

Now we will run the pipeline - Please follow the instructions in the tutorial page.

Step 1 · Download a small sample

cp code/.env.example code/.env   # add credentials; keep local
bash code/01_download_sample.sh 2020 06
  • The downloader reads a product URL, year and month from settings.
  • Raw files go under data/raw/YYYY/MM/.
  • It downloads to a temporary .part file, then renames on success.

Start with one month and one product. It makes troubleshooting and validation manageable.

Download · keep credentials private

ENV_FILE="${ENV_FILE:-$PWD/code/.env}"
[ -f "$ENV_FILE" ] && { set -a; . "$ENV_FILE"; set +a; }
WGETRC="$(mktemp)"; export WGETRC; trap 'rm -f "$WGETRC"' EXIT
printf 'http_user=%s\nhttp_password=%s\n' \
  "$LSASAF_USERNAME" "$LSASAF_PASSWORD" > "$WGETRC"
  • Credentials come from a local .env, never from the repository.
  • wget reads them from a private temporary file, so the password never appears in the process list.

Download · find the month’s files

for d in $(seq -w 1 31); do
  list+=$({ wget -q -O- "$SRC/$YEAR/$MONTH/$d/" || true; } \
          | tr '"' '\n' | grep -E '\.nc$' | sed "s|^|$HOST|" || true)$'\n'
done
  • Loop over possible days; days that do not exist return no listing and are skipped.
  • Keep only .nc links and turn them into full URLs.

Download · safe, parallel, with a time estimate

get() { local f="$2/${1##*/}"
        wget -q -O "$f.part" "$1" && mv "$f.part" "$f"; }
t0=$SECONDS; get "$(head -n1 <<< "$pending")" "$DEST"
tail -n +2 <<< "$pending" \
  | xargs -P "$JOBS" -I{} bash -c 'get "$1" "$2"' _ {} "$DEST"
  • A file only gets its final name when the download is complete; interrupted runs never leave half-files that look finished.
  • Timing the first file gives an estimate for the rest; JOBS sets parallel downloads.

Simplified excerpt: the real script also sets retries and timeouts and reports failed files.

Step 2 · Crop and remap

bash code/02_preprocess_cdo.sh 0.05

The script clips source files using bounds in code/preprocess_utils/config.txt, then remaps using the grid generated from config_resolution.yaml.

Warning

Make the clip bounds and target-grid extent describe the same area. In the current examples they differ; a target grid extending beyond the clipped source can create large missing-value regions.

Processing · key code

command -v cdo >/dev/null || { echo "cdo not found" >&2; exit 1; }
[ -n "$(find "$RAW_DIR" -name '*.nc' -print -quit)" ] || exit 1
bash "$SCRIPT_DIR/cdo_preprocess.sh" "$RESOLUTION" "$RAW_DIR" "$INTERIM_DIR"
  • Fail early: check the tool and the input before doing any work.
  • One call does the work: resolution in, raw files in, interim files out.

Processing · the two CDO operations

cdo sellonlatbox,LON1,LON2,LAT1,LAT2 in.nc cropped.nc   # 1. crop to the area of interest
cdo remapbil,target_grid.txt cropped.nc remapped.nc      # 2. remap to the target grid

Conceptual view of what the pipeline does; the exact calls are in cdo_preprocess.sh.

Resampling is a decision

Method Typical use Main trade-off
Bilinear Continuous fields such as many climate variables Smooths values; can modify extremes
Nearest neighbour Categories and QA flags Preserves classes; can look blocky

Neither method creates finer source detail. For each product, choose a method that matches its values and intended use; retain and apply quality flags where available.

Step 3 · Store for analysis

from zarr.codecs import BloscCodec
INNER_CHUNKS = {"time": 1, "lat": 256, "lon": 256}
SHARD_CHUNKS = {"time": 10, "lat": 512, "lon": 512}
COMPRESSOR = BloscCodec(cname="zstd", clevel=5, shuffle="shuffle")
  • Inner chunks are the read units: one date and a spatial window.
  • Shards group chunks to reduce the number of storage objects.
  • Compression makes the store smaller; these settings are starting points.

Run the builder with uv run python code/build_zarr_cube.py. It expects interim dimensions named time, lat, and lon; it replaces its existing output store when rebuilding.

Zarr · chunks decide which queries are fast

Query What it reads with time=1 chunks Cost
Map for one date A few spatial chunks of one time step Low
Time series at one cell One chunk per time step More, smaller reads

Benchmark the actual map and time-series queries before choosing final chunk and shard sizes.

Inspect a cube

import xarray as xr
ds = xr.open_zarr("data/zarr/metref_sample_1month.zarr")
field = next(iter(ds.data_vars))
map_for_date = ds[field].isel(time=0)
series_at_cell = ds[field].isel(lat=100, lon=100)

The cell indices are illustrative. Check coordinate names, coordinate direction, units and timestamps before interpreting values. Use the reusable functions in code/plot_utils/ for maps and temporal plots.

5 · Limitations and caveats

What the cube does not solve

Caveats and uncertainty

  • Missing values may be real masks/quality exclusions or processing/configuration problems.
  • A crop/grid mismatch, wrong variable, coordinate issue or fill-value handling can cause extensive NaNs.
  • Bilinear remapping smooths; nearest-neighbour can be blocky. Different choices can change statistics.
  • Degree grids have latitude-dependent ground dimensions.
  • Product versions, temporal support, units and quality systems may differ.
  • The example is a regional teaching workflow, not a validated operational climate product.

On-the-fly processing vs a pre-built cube

On-the-fly (catalog + lazy loading) Pre-built cube (this tutorial)
Regridding / resampling Done at read time; settings are easy to overlook Fixed once and documented in the pipeline
Compute cost Paid at every query Paid once, up front
Storage Reuses the provider’s data Creates a derived copy
Changing area, grid or method Change the query Re-run the pipeline
Following provider updates Automatic Needs a rebuild

Neither is better in general. Choose by use case, and always record the resampling choice.

Scale the pilot carefully

For a large domain (for example, a 2,000 km corridor), first benchmark a representative priority subset:

  • Record runtime, peak memory, file size, valid coverage and output read speed.
  • Split work into grid-aligned spatial tiles and/or time batches.
  • Parallelize independent files within measured CPU, memory and I/O limits.
  • Add remapping margins at tile edges and trim duplicate target cells.
  • Write non-overlapping Zarr regions or isolated stores; track and retry failures.

Do not scale only by multiplying worker count. Disk throughput, memory, output object counts and safe Zarr writes can become the bottleneck.

Possible next updates

  • Harmonize clip and target-grid bounds; add a coverage map and threshold.
  • Apply product-specific quality flags and test decoded no-data values.
  • Record provenance, product versions, units, grid and resampling settings.
  • Benchmark chunk/shard sizes for intended queries and available compute/storage.
  • Add more products only after documenting their spatial and temporal semantics.
  • Add automated tests for sample input files and failed/partial outputs.

What we learned

A useful climate cube starts with consistent, documented choices and honest checks on missing data and resolution.
