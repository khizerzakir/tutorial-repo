Why are we here?

Climate products are useful, but their files can arrive with different grids, time steps, metadata and quality information.

Today we make one small, transparent processing path from EUMETSAT source files to a regional data cube.

What will we learn?

  • Crop and remap a sample to an explicitly defined regional grid. {.fragment .fade-up}
  • Build and inspect a chunked, compressed Zarr cube. {.fragment .fade-up}

What is a climate data cube?

A data cube is a multidimensional way to organize data. A climate data cube applies this idea to climate or Earth observation variables, commonly indexed by:

time × space × variable

  • Generic cube: the same structure can store many domains and measurements.
  • Climate cube: gives climate/EO data meaningful variables, units, calendars, grids, quality flags, provenance and uncertainty.
  • It is a domain-focused data organization, not a separate file format. Here, NetCDF is the input and Zarr is the output.

Each step leaves a checkable output. If a stage fails, diagnose that stage before moving on.

Step 1 · Download a small sample

cp code/.env.example code/.env   # add credentials; keep local
bash code/01_download_sample.sh
  • The downloader reads a product URL, year and month from settings.
  • Raw files go under data/raw//YYYY/MM/.
  • It downloads to a temporary .part file, then renames on success.

Start with one month and one product. It makes troubleshooting and validation manageable.

Step 2 · Crop and remap

bash code/02_preprocess_cdo.sh 0.05

The script clips source files using bounds in code/preprocess_utils/config.txt, then remaps using the grid generated from config_resolution.yaml.

Warning

Make the clip bounds and target-grid extent describe the same area. In the current examples they differ; a target grid extending beyond the clipped source can create large missing-value regions.

Resampling is a decision

Method Typical use Main trade-off
Bilinear Continuous fields such as many climate variables Smooths values; can modify extremes
Nearest neighbour Categories and QA flags Preserves classes; can look blocky

Neither method creates finer source detail. For each product, choose a method that matches its values and intended use; retain and apply quality flags where available.

Step 3 · Store for analysis

INNER_CHUNKS = {"time": 1, "lat": 256, "lon": 256}
SHARD_CHUNKS = {"time": 10, "lat": 512, "lon": 512}
COMPRESSOR = BloscCodec(cname="zstd", clevel=5, shuffle="shuffle")
  • Inner chunks are the read units, for example one date and a spatial window.
  • Shards group chunks to reduce the number of storage objects.
  • These settings are starting points; benchmark the actual map and time-series queries.

Run the builder with uv run python code/build_zarr_cube.py. It expects interim dimensions named time, lat, and lon; it replaces its existing output store when rebuilding.

Inspect a cube

import xarray as xr

ds = xr.open_zarr("data/zarr/metref_sample_1month.zarr")
field = next(iter(ds.data_vars))
map_for_date = ds[field].isel(time=0)
series_at_cell = ds[field].isel(lat=100, lon=100)

The cell indices are illustrative. Check coordinate names, coordinate direction, units and timestamps before interpreting values. Use the reusable functions in code/plot_utils/ for maps and temporal plots.

QA · what should we check?

  • Compare source and output coordinates, timestamps, units and variable names.
  • Check decoded fill values and valid-cell count/fraction.
  • Plot the missing-data footprint; compare it with the source mask and QA flags.
  • Compare a few known source/output values and summary statistics.
  • Reopen Zarr and compute a small selection before processing more data.

A file that opens is not automatically fit for analysis. Non-zero valid values do not by themselves prove sufficient spatial coverage.

What can the cube support?

  • Regional and seasonal climate maps.
  • Spatial summaries and time series for locations or zones.
  • Evapotranspiration and vegetation monitoring.
  • Inputs to climate-impact or resilience indicators after domain validation.

The cube makes data access more consistent; scientific interpretation still depends on product quality, aggregation choices and validation.

Caveats and uncertainty

  • Missing values may be real masks/quality exclusions or processing/configuration problems.
  • A crop/grid mismatch, wrong variable, coordinate issue or fill-value handling can cause extensive NaNs.
  • Bilinear remapping smooths; nearest-neighbour can be blocky. Different choices can change statistics.
  • Degree grids have latitude-dependent ground dimensions.
  • Product versions, temporal support, units and quality systems may differ.
  • The example is a regional teaching workflow, not a validated operational climate product.

APIs, cloud platforms and this workflow

APIs, Microsoft Planetary Computer and Google Earth Engine are useful for discovering, accessing and analyzing many datasets.

This tutorial demonstrates a local, explicit path for selected authenticated LSA SAF data when we need to document a regional crop, target grid and processing choices. The two approaches can complement each other; this workflow does not assume hosted platforms lack the required data.

Scale the pilot carefully

For a large domain (for example, a 2,000 km corridor), first benchmark a representative priority subset:

  • Record runtime, peak memory, file size, valid coverage and output read speed.
  • Split work into grid-aligned spatial tiles and/or time batches.
  • Parallelize independent files within measured CPU, memory and I/O limits.
  • Add remapping margins at tile edges and trim duplicate target cells.
  • Write non-overlapping Zarr regions or isolated stores; track and retry failures.

Do not scale only by multiplying worker count. Disk throughput, memory, output object counts and safe Zarr writes can become the bottleneck.

Possible next updates

  • Harmonize clip and target-grid bounds; add a coverage map and threshold.
  • Apply product-specific quality flags and test decoded no-data values.
  • Record provenance, product versions, units, grid and resampling settings.
  • Benchmark chunk/shard sizes for intended queries and available compute/storage.
  • Add more products only after documenting their spatial and temporal semantics.
  • Add automated tests for sample input files and failed/partial outputs.

What we learned

A useful climate cube starts with consistent, documented choices and honest checks on missing data and resolution.
