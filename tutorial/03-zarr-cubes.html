C · Build the Zarr cube

Chunk, shard, compress — and choose the layout for your questions

A · Setup B · Download & preprocess C · Zarr cube D · Explore

code/03_build_zarr_cube.py turns the interim NetCDF files of one product into a single Zarr v3 store: one time axis, one grid, compressed chunks grouped into shards, with consolidated metadata so it opens instantly.

1 · Preview the plan (dry run)

Always look before you write. --dry-run opens the files lazily and prints what would be built:

uv run python code/03_build_zarr_cube.py --input data/interim/METREF --dry-run
Profile          : map
Files            : 30  (…201506010000_processed.nc … …201506300000_processed.nc)
Variables        : METREF, quality_flag
Dimensions       : {'time': 30, 'lat': 91, 'lon': 121}
Time range       : 2015-06-01 → 2015-06-30
Inner chunk      : {'time': 1, 'lat': 91, 'lon': 121}  (~43.0 KB raw each)
Shard            : {'time': 10, 'lat': 91, 'lon': 121}
Per variable     : 30 inner chunks in 3 shard object(s)
Uncompressed size: 1.9 MB
Output           : …/data/zarr/metref_cube.zarr

Dry run: nothing written.

2 · Build

uv run python code/03_build_zarr_cube.py --input data/interim/METREF
…
Validation OK    : first/last time steps match the interim NetCDF
Valid fraction   : METREF=95.9%, quality_flag=100.0%
Stored size      : 841.8 KB in 15 files (compression ≈ 2.3× vs 1.9 MB in memory)
Done in 3.3s → …/data/zarr/metref_cube.zarr

What happens, in order:

Open lazily. All *_processed.nc files under --input are opened with xarray + Dask, concatenated along time in file-name order (no coordinate re-alignment — they share one grid, which is verified against the last file).

Plan chunks. Inner chunks and shards come from the --profile; shards are rounded to whole multiples of the inner chunk (a Zarr v3 requirement) and clamped to the data size.

Write safely. Dask writes whole shards in parallel to <output>.tmp. Stale NetCDF encodings are dropped; provenance (zarr_cube_* attributes) is added.

Validate, then swap. The first and last time steps are compared value-by-value with their source files. Only then is the old cube replaced — a failed run never destroys a working cube.

3 · Options

Flag Default Use it to…
--input DIR data/interim point at one product’s interim folder
--pattern GLOB *_processed.nc select files, e.g. '*201506*_processed.nc'
--output PATH data/zarr/<variable>_cube.zarr name the store
--variables V … all keep only some variables, e.g. --variables METREF
--profile map pick a chunk layout: map, balanced, timeseries
--chunks / --shards from profile fine-tune, e.g. --chunks time=4,lat=64,lon=64
--clevel 1-9 5 zstd level: higher = smaller but slower to write
--float32 off store float64 data as float32 (half the size)
--workers N all cores limit CPU threads on shared machines
--append off add only newer time steps to an existing cube
--no-consolidate off skip consolidated metadata (portability over speed)
--dry-run off print the plan and exit

Grow the cube month by month without rebuilding:

bash code/01_download_sample.sh 2015 07 METREF
MAIN_VARIABLE=METREF uv run bash code/02_preprocess_cdo.sh 0.05 data/raw/METREF data/interim/METREF
uv run python code/03_build_zarr_cube.py --input data/interim/METREF --append

4 · Explore the chunk layout

Chunks decide which questions are cheap. A single-date map should touch few chunks; a long time series at one pixel should too — but one layout cannot make both minimal. Change the cube size and profile and watch what each query has to read.

--profile

Rules of thumb

  • Aim for inner chunks of roughly 100 KB – a few MB (uncompressed). Tiny chunks mean many requests; huge chunks mean reading data you do not need.
  • Map-heavy work (daily maps, animations): --profile map. Time-series-heavy work (pixel/zone trends, anomalies): --profile timeseries. Unsure: balanced.
  • Shards reduce the number of files/objects (important on laptops, HPC and object storage); they do not change what is decompressed.
  • Benchmark your real queries before scaling up — these profiles are starting points, not optima.

6 · Troubleshooting

Symptom Fix
No files matching '*_processed.nc' Run step B, or point --input at the right folder
Duplicate timestamps found Two products or two runs in one folder — use --input data/interim/<PRODUCT>
Expected dimensions ('time','lat','lon') Your files use other names; latitude/longitude/x/y are renamed automatically, others need preprocessing
Zarr >= 3.0 is required Run through uv run … (project environment)
different lat grid than … Files were processed with different AOIs — delete the folder and rerun step B
Slow on WSL Keep the repository in ~/…, not /mnt/c/…; limit --workers if RAM is tight

7 · Scaling beyond the sample

For a larger region or many years: benchmark a representative subset (runtime, peak memory, stored size, read speed of your real queries), then process in time batches and grow the cube with --append. For very large areas split into grid-aligned tiles with a remapping margin, write each to its own store or to non-overlapping Zarr regions, and keep a manifest so only failed batches are re-run.
